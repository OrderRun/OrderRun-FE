# Harness Metrics

Aggregated token-usage and quality metrics for the multi-agent Harness in
`.harness/`. Generated by `npm run harness:usage:snapshot` from a local,
gitignored raw history; only the aggregates in this directory are committed.

| file | contents |
|---|---|
| `history.csv` | one row per (date, harnessVersion, provider, lane, role) with averages and sample sizes |
| `summary.json` | roll-up by Harness version, provider, Lane and role, plus version-over-version comparison |

## How the data is produced

`npm run harness:monitor` runs a local Node script that reads the usage counters
the Claude Code and Codex runtimes already write to disk, normalizes them into
one schema, and appends them to `.harness/metrics/raw/usage-history.jsonl`.

**Monitoring makes 0 AI calls.** No analyzer agent, no extra prompt, no
transcript content in any model context — measuring the Harness must not consume
the thing it measures.

Nothing identifying is recorded: no prompts, responses, transcript bodies, source
code, environment values, keys or emails. Run slugs, session ids and transcript
paths exist only in the local raw file and are removed by aggregation before
anything lands here.

## Reading the numbers

- `processedTokens` = fresh input + output + cache read + cache write. It is a
  raw throughput counter. **It is not billing cost, not subscription usage, and
  not actually charged tokens.**
- Provider columns are a raw token-processing comparison. No pricing model is
  applied, so no cost conclusion about one provider versus the other follows
  from them.
- `sampleSize` / `runCount` / `n` are printed everywhere on purpose. A
  difference across Harness versions with a handful of runs behind it is not
  evidence; `summary.json` refuses to compute a change percentage below 3 runs
  per version.
- Quality columns (`firstPassRate`, `avgRevisionRounds`, `verificationPassRate`)
  come from the reviewer artifacts the Harness already produces, so a token
  reduction can be judged against whether review quality held.

## What this is for

Comparing Harness versions on the same metrics — per-role and per-Lane token
usage, per-run totals, revision rounds and first-pass review rate — so structural
changes to the Harness (context scoping, agent count, progressive disclosure) can
be evaluated on measurements instead of impressions. Interpretation and any
resulting rule change are a human decision, made through `.harness/evolution/`.

# OrderRun-FE 프로젝트 규칙 (살아있는 문서)

이 파일은 **하네스의 규칙 축적 지점**이자 **프로젝트 기본 정보의 확정 기록**이다. 개발 중 반복되는 실수나 새로 정해진 규칙은 여기에 추가한다.
아직 정해지지 않은 것은 "미확정"으로 남겨둔다. 미확정 항목을 추측으로 채우지 않는다.

> **재조사 금지:** 1·2절의 스택·컴파일러 제약·검증 명령은 확인된 사실이다. 에이전트는 매 작업마다 `package.json`·`tsconfig*.json`·`eslint.config.js`를 다시 열지 않는다. 새 의존성이 필요하거나 이 문서가 실제와 다르다고 의심될 때만 원본을 확인하고, 다르면 이 문서를 갱신한다.

## 목차
1. 스택 사실
2. 컴파일러 제약 (자주 걸리는 것)
3. 디렉토리 배치 규칙
4. 계층 규칙 (UI / 데이터 / 도메인)
5. 추상화 억제 규칙
6. 미확정 항목
7. 규칙 추가 로그

## 1. 스택 사실

검증 시점: 2026-08-20. 변경 시 이 절을 갱신한다.

| 항목 | 값 |
|------|-----|
| React | 19.x (`react`, `react-dom`) |
| TypeScript | 6.0.x |
| 빌드 도구 | Vite 8.x + `@vitejs/plugin-react` |
| Lint | ESLint 10 (flat config) + typescript-eslint 8 + eslint-plugin-react-hooks 7 + eslint-plugin-react-refresh |
| 테스트 러너 | **없음** (미도입) |
| 라우터 / 상태관리 / 데이터 fetch / UI 라이브러리 | **없음** (미도입) |

**`package.json`의 `dependencies`에 없는 라이브러리는 사용할 수 없다.** 필요하면 설치를 제안하고 승인을 받는다.

검증 명령 (`package.json` scripts):

| 명령 | 내용 |
|------|------|
| `npm run typecheck` | `tsc -b --noEmit` |
| `npm run lint` | `eslint . --max-warnings 0` (경고도 실패로 처리) |
| `npm run build` | `tsc -b && vite build` |
| `npm run dev` | Vite 개발 서버 |
| `npm run preview` | 빌드 결과 미리보기 |

## 2. 컴파일러 제약 (자주 걸리는 것)

`tsconfig.app.json` 설정에서 실제로 코드 작성 방식을 바꾸는 항목들이다.

| 설정 | 값 | 코드에 미치는 영향 |
|------|-----|-------------------|
| `strict` | true | `any` 우회 금지. null/undefined를 명시적으로 다룬다 |
| `verbatimModuleSyntax` | true | 타입만 import할 때 `import type { X } from './x'` 필수. 값과 타입을 한 import 문에 섞으면 에러 |
| `erasableSyntaxOnly` | true | **`enum`, `namespace`, 생성자 파라미터 프로퍼티 사용 불가.** 상수 집합은 `as const` 객체 + 유니온 타입으로 표현한다 |
| `noUnusedLocals` / `noUnusedParameters` | true | 미사용 변수·매개변수는 **컴파일 에러**. 자리표시자 매개변수는 `_` 접두사 |
| `noFallthroughCasesInSwitch` | true | switch case 폴스루 금지 |
| `moduleResolution` | bundler | 경로 별칭 미설정 — 현재는 상대 경로만 사용 |
| `jsx` | react-jsx | `import React` 불필요 |

`enum` 대신 쓰는 형태 (문법 예시일 뿐이며, 아래 값은 이 프로젝트의 확정 도메인 값이 **아니다**):

```ts
export const SORT_ORDER = {
  Asc: 'asc',
  Desc: 'desc',
} as const

export type SortOrder = (typeof SORT_ORDER)[keyof typeof SORT_ORDER]
```

ESLint 관련 주의:
- `react-refresh/only-export-components` — 컴포넌트 파일에서 컴포넌트 외의 값을 export하면 경고가 나고, `--max-warnings 0`이므로 **검증이 실패한다.** 상수·타입·훅은 별도 파일로 분리한다.
- `react-hooks` 최신 규칙 세트가 켜져 있다. 훅 호출 순서, 의존성 배열, ref 취급에 대한 경고도 실패로 처리된다.

## 3. 디렉토리 배치 규칙

현재 실재하는 구조:

```
src/
  main.tsx     — 엔트리
  App.tsx      — 루트 컴포넌트
  index.css    — 전역 스타일
```

**Feature-based 배치를 지향한다. 단, 폴더는 파일이 들어갈 때 만든다.** 빈 폴더나 선점용 폴더를 만들지 않는다.

기능이 추가될 때의 배치 원칙:

| 대상 | 위치 | 조건 |
|------|------|------|
| 특정 기능에만 쓰이는 컴포넌트/훅/타입/로직 | `src/features/{feature}/` | 기본값. 대부분 여기 |
| 두 개 이상의 feature가 실제로 쓰는 UI | `src/shared/` (또는 합의된 위치) | **두 번째 사용처가 실제로 생겼을 때 이동** |
| 앱 전역 설정(라우터, provider 등) | `src/app/` | 해당 기술이 도입되었을 때 |

feature 내부 세분화(`components/`, `hooks/`, `api/` 등)는 **파일이 5개를 넘어 탐색이 불편해질 때** 도입한다. 파일 2~3개짜리 feature를 미리 3단 폴더로 나누지 않는다.

> **파일 수 하한은 lint가 정한다.** `react-refresh/only-export-components` + `--max-warnings 0` 조합 때문에 컴포넌트 파일에서 상수·타입·훅을 함께 export할 수 없다. 따라서 상태 상수 + 타입 + 순수 함수를 갖는 기능은 **파일이 3~4개가 되는 것이 정상**이며, 이는 과잉 분리가 아니다. "파일 수가 많다"는 이유로 이 분리를 되돌리면 검증이 실패한다. 줄여야 할 것은 **책임이 없는 파일**(래퍼, 구현체 하나뿐인 인터페이스, 선점용 배럴 파일)이지 lint가 강제한 분리가 아니다.

## 4. 계층 규칙 (UI / 데이터 / 도메인)

목적은 계층을 만드는 것이 아니라 **컴포넌트를 테스트 가능하고 재사용 가능하게 유지**하는 것이다.

| 종류 | 어디에 | 이유 |
|------|--------|------|
| 렌더링, 사용자 입력 처리, 로컬 UI 상태 | 컴포넌트 안 | UI의 본래 책임 |
| 데이터 fetch / 캐싱 / 요청 상태 | 컴포넌트 밖의 훅 | 화면 여러 곳에서 재사용, 컴포넌트 테스트 가능성 확보 |
| 순수 도메인 판정·계산·변환 (상태 전이 가능 여부, 표시용 라벨 매핑, 필터링 규칙) | 컴포넌트 밖의 순수 함수 | React 없이 테스트 가능해야 한다 |
| 서버 응답 ↔ 화면 타입 변환 | 데이터 레이어 경계 한 곳 | 변환을 여러 곳에서 하면 필드명 불일치가 퍼진다 |

판정 기준: **"이 로직을 테스트하려면 컴포넌트를 렌더해야 하는가?" 그렇다면 잘못 배치된 것이다.**

## 5. 추상화 억제 규칙

이 프로젝트는 Clean Architecture를 사용하지 않는다. Repository / UseCase / Entity / Service 계층을 이유 없이 만들지 않는다.

새 파일·새 추상화를 만들기 전에 통과해야 하는 질문:

1. 지금 이 기능에 **실제로** 필요한가? (미래 대비는 근거가 아니다)
2. 이 파일을 없애면 무엇이 깨지는가? 답하지 못하면 만들지 않는다.
3. 사용처가 몇 곳인가? **1곳이면 공용화하지 않는다.**
4. 인터페이스를 만들면서 구현체가 하나뿐인가? 그러면 인터페이스를 만들지 않는다.

중복 처리 원칙: 같은 도메인 로직이 두 번째 화면에 필요해지면 **복사하지 말고 공용 위치로 옮긴다.** 세 번째까지 기다리지 않는다. 도메인 판정 로직의 중복은 데이터 불일치로 직결되기 때문이다.

## 6. 미확정 항목

아래는 아직 정해지지 않았다. **추측해서 코드에 반영하지 않는다.** 필요해지는 시점에 사용자에게 확인하고, 확정되면 이 문서에 옮긴다.

| 항목 | 상태 |
|------|------|
| 백엔드 API 베이스 URL / 인증 방식 | 미확정 |
| Request / Application / Mission / Dispute 의 데이터 스키마와 상태 값 | 미확정 |
| 라우터 도입 여부와 라이브러리 | 미확정 |
| 서버 상태 관리 방식 (fetch 직접 / TanStack Query 등) | 미확정 |
| UI 라이브러리 · 스타일링 방식 (현재 순수 CSS) | 미확정 |
| 테스트 러너 (Vitest 등) 도입 여부 | 미확정 |
| 경로 별칭(`@/`) 도입 여부 | 미확정 |

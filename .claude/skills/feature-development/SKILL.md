# Feature Development — 계획 + 구현

A장은 planner, B장은 feature-implementer가 따른다. 프로젝트 확정 규칙은 `references/project-conventions.md`에 있으며 **작업 전 반드시 읽는다.**

## 토큰 원칙 (양쪽 공통)

- `references/project-conventions.md`에 적힌 스택·컴파일러 제약·검증 명령은 **이미 확인된 사실**이다. `package.json`·`tsconfig`·`eslint.config.js`를 매번 다시 열지 않는다. 새 의존성이 필요하거나 문서가 실제와 다르다고 의심될 때만 확인한다.
- 코드베이스 전체를 훑지 않는다. planner는 검색에 걸린 파일만, implementer는 계획의 "관련 파일"과 수정 대상만 읽는다.
- 문서는 결정·변경·실패 중심으로 짧게. 앞 문서에 있는 내용을 뒤 문서에 되풀이하지 않는다.
- 검증 로그 전문을 컨텍스트에 넣지 않는다. exit code와 에러 줄만 본다.

# A. 계획 (planner)

산출물: `_workspace/{slug}/plan.md` — **80줄 이내**

## A-1. 조사 (최소 읽기)

1. `references/project-conventions.md`
2. 요구사항의 도메인/UI 용어로 `src/` 검색 (전용 검색 도구가 없으면 `grep -rIn "패턴" src`, `find src -type f`)
3. **걸린 파일만** 읽는다. 0건이면 "신규 영역"으로 확정하고 끝낸다

## A-2. 추측 금지

API 엔드포인트·응답 스키마·필드명·상태 값·권한 규칙·화면 이동 경로는 **근거 없이 지어내지 않는다.** "확인 필요"로 올린다.

추측한 shape은 TypeScript 캐스팅을 통과해 typecheck·build를 모두 통과하고 런타임에 깨진다. **이 프로젝트의 자동 검증으로는 원리적으로 잡히지 않는** 유일한 결함 부류이므로 여기서 막는 것이 가장 싸다.

## A-3. 파일과 추상화

각 파일에 "필요한 이유"를 한 줄로 적는다. 못 쓰면 그 파일을 뺀다. 미래 확장성은 이유가 아니다.

- 배치는 `references/project-conventions.md` 3절 (기본값 `src/features/{feature}/`, 폴더는 파일이 들어갈 때)
- 사용처 1곳이면 공용화하지 않는다. 구현체 하나뿐인 인터페이스를 만들지 않는다
- Repository / UseCase / Entity 계층을 습관적으로 만들지 않는다
- 단, **lint가 정한 파일 수 하한**은 과잉 분리가 아니다 (`references/project-conventions.md` 3절 참조)

## A-4. UI / 데이터 분리

판정 기준 하나: **"이 로직을 테스트하려면 컴포넌트를 렌더해야 하는가?"** 그렇다면 밖으로 뺀다.
컴포넌트 안 = 렌더링·이벤트·로컬 UI 상태 / 밖 = 데이터 fetch(훅), 도메인 판정·계산·변환(순수 함수).

## A-5. 계획 템플릿

```markdown
# Plan: {기능명}

## 목표 / 비목표
## 완료 판정 기준
- (관찰 가능한 문장. "잘 동작한다"는 기준이 아니다)

## 관련 파일 (하류 에이전트의 읽기 목록)
| 경로 | 왜 관련 있는가 |
(없으면 "신규 영역 — 관련 기존 코드 없음")

## 전제 / 확인 필요
| 항목 | 근거 또는 미확인 | 틀렸을 때 영향 |

## 파일 계획
| 경로 | 신규/수정 | 단일 책임 | 필요한 이유 |

## 타입 계약
```ts
// 경계를 넘는 타입만. 구현 본문 없음
```

## UI / 데이터 분리
- 컴포넌트 밖으로: (무엇을 어느 파일로, 근거 한 단어)

## 경계 상태
| 상황 | 기대 동작 |
| 로딩 중 | |
| 실패 | |
| 빈 데이터 | |
| 잘못된 입력 / 권한 없음 | |

## 검증 기준
- 자동: typecheck / lint / build
- 기능: (관찰 가능한 조건)
```

**경계 상태 표를 비우면 계획은 미완성이다.** 계획에 없으면 구현되지 않고, 구현되지 않으면 리뷰가 지적할 근거도 없다. 그리고 이것은 typecheck/lint/build로 절대 잡히지 않는다.

# B. 구현 (feature-implementer)

산출물: `src/` 코드 + `_workspace/{slug}/impl.md` — **30줄 이내**

## B-1. 시작 전

`plan.md` → `references/project-conventions.md` 2절(컴파일러 제약) → **계획의 "관련 파일"과 수정 대상 파일만** 읽는다. 덮어쓰기 전에는 반드시 현재 내용을 읽는다.

## B-2. 계획대로

계획에 있는 파일만 만든다. 추가가 필요하면 만들지 말고 계획 변경을 요청한다. 계획의 타입 계약을 편의를 위해 느슨하게 바꾸지 않는다. **경계 상태 표를 한 행씩 코드로 옮긴다** — 정상 경로만 만들고 끝내지 않는다.

## B-3. 추측 금지

데이터 shape이 미확정이면 **멈추고 질문한다.** (이유는 A-2와 같다)

## B-4. 억제 수단

`any` / `as` / `@ts-ignore` / `eslint-disable`로 에러를 덮지 않는다. 불가피하면 사유 주석 + `impl.md` 기록. 기록 없는 억제는 리뷰에서 MAJOR다.

## B-5. 자체 검증

세 명령을 개별 실행하고 exit code를 확인한다. 로그는 파일로 리다이렉트하고, 실패 시에만 에러 줄을 뽑아 본다. 실패한 상태로 리뷰에 넘기지 않는다 — 라운드 낭비다. 3회 시도해도 못 고치면 에스컬레이션한다.

**자체 검증 통과는 "완료"가 아니다.** 완료 판정은 reviewer의 PASS로만 성립한다.

## B-6. 수정 라운드

**지적된 항목만** 고친다. 전면 재작성 금지. 각 지적에 **수정함 / 반박함(근거) / 계획 변경 필요** 중 하나로 답한다.

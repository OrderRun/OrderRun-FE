# Review & Verify — 통합 판정 게이트

"완료"라고 말할 수 있는 유일한 근거는 **명령의 exit code + 계획 대비 리뷰**다. 자기 판단이나 "문제 없어 보임"은 판정이 아니다.

산출물: `_workspace/{slug}/review_r{N}.md` — **40줄 이내**, 라운드마다 새 파일 (덮어쓰기 금지)

**쓰기 범위:** 이 리포트 하나뿐. `src/`·설정 파일 수정 금지. 게이트를 통과시키려고 `tsconfig`/`eslint.config.js`를 완화하는 것은 검증의 무효화다.

## 왜 검증을 먼저 돌리는가

검증과 리뷰를 따로 넘기면 수정 라운드가 두 배가 된다. 검증을 먼저 실행해 실패 항목을 확보한 뒤 리뷰를 붙여 **한 묶음의 수정 지시**로 만든다.

## 1단계 — 검증 게이트

실행 전 `package.json`의 `scripts`를 확인한다. 새 검증 명령이 생겼을 수 있고, 없는 명령을 추측 실행하면 안 되기 때문이다.

| 게이트 | 명령 | 상태 |
|---|---|---|
| 타입 | `npm run typecheck` (`tsc -b --noEmit`) | 필수 |
| lint | `npm run lint` (`eslint . --max-warnings 0`) | 필수 — **경고도 실패** |
| 빌드 | `npm run build` (`tsc -b && vite build`) | 필수 |
| 테스트 | `npm run test` | **미도입.** `test` 스크립트가 생기면 즉시 필수로 추가 |

```
npm run typecheck > _workspace/{slug}/.verify.log 2>&1; echo "typecheck: $?"
npm run lint      >> _workspace/{slug}/.verify.log 2>&1; echo "lint: $?"
npm run build     >> _workspace/{slug}/.verify.log 2>&1; echo "build: $?"
```

규칙:
- **`&&`로 묶지 않는다.** 첫 실패에서 멈추면 세 곳이 깨졌는데 한 곳만 보고하게 되고, 한 라운드에 고칠 것을 세 라운드에 걸쳐 고치게 된다
- **파이프를 쓰지 않는다.** `| tee`는 `tee`의 exit code를 읽어 판정을 무의미하게 만든다. 리다이렉션을 쓰거나 `${PIPESTATUS[0]}`을 읽는다
- **로그 전문을 컨텍스트에 넣지 않는다.** 실패 시에만 `grep -nE "error|✖|Error:" _workspace/{slug}/.verify.log | head -20`
- `tsc -b`는 증분 빌드다(`node_modules/.tmp`). 정상이지만, 코드가 바뀌었는데 결과가 이전 라운드와 완전히 동일해 의심스러우면 `rm -rf node_modules/.tmp` 후 재실행한다
- 실패 분류: 타입 오류 / lint 위반 / 빌드 오류 / **설정 문제** / **환경 문제**. 뒤 둘은 임의 수정하지 말고 에스컬레이션한다

## 2단계 — 리뷰

자동 검증이 이미 잡는 것(타입·lint·빌드 오류)을 다시 지적하지 않는다. 리뷰의 존재 이유는 **검증이 전부 통과해도 남는 결함**이다.

**읽는 범위:** `plan.md` + `impl.md` + **변경된 파일만** (`git status --porcelain -- src`). 코드베이스 전체를 훑지 않는다. 코드를 리포트에 붙여넣지 않는다(위치만).

### 경계면 교차 검토

한쪽만 읽으면 양쪽 다 올바르게 보여 절대 잡히지 않는다. **동시에 열어** 비교한다.

| 대상 | 생산자 | 소비자 |
|---|---|---|
| 데이터 shape | 만드는 함수의 실제 반환값 | 쓰는 훅/컴포넌트의 기대 타입 |
| 상태 값 | 상태 문자열 정의 | `if (status === 'x')` 분기 |
| props 계약 | 컴포넌트 props 타입 | 호출부가 넘기는 값 |

`as`·제네릭 캐스팅·`any`가 낀 경계가 우선 대상이다 — 타입 검사를 통과해도 런타임에 깨진다.

### 체크리스트

- [ ] **요구사항 누락** — 계획의 완료 판정 기준 각 항목이 충족되는가
- [ ] **경계 상태 표 각 행**이 구현되었는가 (행 단위 확인)
- [ ] 추측으로 지어낸 데이터 shape이 없는가
- [ ] 계획에 없는 파일이 생기지 않았고, 계획된 파일이 계획된 책임을 지키는가
- [ ] 컴포넌트에 fetch·변환·도메인 판정이 섞이지 않았는가
- [ ] 같은 도메인 로직이 두 곳에 있지 않은가
- [ ] 억제 사용이 `impl.md`에 기록되고 사유가 타당한가
- [ ] 구현체 하나뿐인 인터페이스, 없애도 안 깨지는 파일이 없는가

## 3단계 — 판정

| 등급 | 기준 |
|---|---|
| BLOCKER | 런타임 실패, 데이터 계약 불일치, 추측 기반 코드, 구조에 관한 계획 위반, 요구사항 누락 |
| MAJOR | 경계 상태 누락, UI/데이터 혼재, 중복 구현, 근거 없는 억제, 과잉 추상화 |
| MINOR | 명명, 배치, 가독성 |

**PASS = 검증 3종 exit 0 AND BLOCKER 0 AND MAJOR 0.** 그 외는 FIX_REQUIRED.

각 지적에 위치(`파일:라인`) / 근거 / **실패 시나리오**(어떤 입력·상태에서 무엇이 잘못되는가) / 수정 지시를 적는다. 실패 시나리오를 못 쓰는 BLOCKER는 등급을 낮춘다. 인용한 위치가 실재하는지 재확인한다.

**검증하지 못한 영역을 PASS라고 하지 않는다.** 읽지 못한 파일, 실행하지 못한 검증은 "미검증"에 명시하고, PASS를 선언할 때 그 사실을 함께 반환한다. 실행하지 않은 검증을 통과한 것처럼 보이게 하는 것이 이 게이트에서 가장 위험한 실패다.

## 리포트 템플릿

```markdown
# Review (round {N})

## 검증
| 명령 | exit | 판정 |
실패 시 핵심 오류만: `파일:라인 — 규칙/코드 — 메시지`

## 판정
PASS | FIX_REQUIRED  (BLOCKER {n} / MAJOR {n} / MINOR {n})

## 지적
### [BLOCKER-1] {한 줄}
- 위치 / 근거 / 실패 시나리오 / 수정 지시

## 미검증
- test: 러너 미도입
- 런타임 동작: 정적 검사만 수행함
- (읽지 못한 파일이 있으면 명시)
```

## 테스트가 도입되면

`package.json`에 `test` 스크립트가 추가되는 순간 고칠 곳은 **두 곳뿐**이다: 이 문서 1단계의 게이트 표, 그리고 `.claude/skills/feature-development/references/project-conventions.md`의 검증 명령 표. 다른 곳에 검증 명령을 하드코딩하지 않는다.

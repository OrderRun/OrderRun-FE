# Shared Agent Token Usage Schema

Provider-agnostic contract for the Harness usage observability layer. Claude and
Codex collectors must both emit this exact shape. Nothing here may reference a
provider-specific transcript path or field name; that belongs in the provider
adapter.

This layer is observability only. It never changes role permissions, Lane
selection, the Mutation Guard, or the Verification Gate.

## Unit of measurement

One record = one **agent invocation**: a single spawn of a Harness role that ran
to completion. A fix round is a separate invocation, never a merge into the
previous one.

## Invocation identity

`invocationId = "{role}-r{round}"` — e.g. `planner-r1`, `implementer-r1`,
`reviewer-r1`, `implementer-r2`, `reviewer-r2`.

`provider + invocationId` is unique inside one run. Re-collecting that pair
overwrites its record in place; it never appends. Within one provider,
`sourceId` must not appear under two different invocations — that indicates the
collector matched a stale transcript and must be a monitoring warning.

## Roles

| role | meaning |
|---|---|
| `planner` | canonical `roles/planner.md` invocation |
| `implementer` | canonical `roles/implementer.md` invocation |
| `reviewer` | canonical `roles/reviewer.md` invocation, including the verification gate |
| `orchestrator` | the top-level driving session, when measured separately |

Provider-internal agent names are mapped to these logical roles by the adapter.
No other role value is written.

## Token fields

Each field is preserved separately. They are **not** interchangeable and are
**not** cost.

| field | meaning |
|---|---|
| `inputTokens` | fresh prompt tokens after provider cache fields are separated |
| `outputTokens` | tokens generated by the model |
| `cachedInputTokens` | prompt tokens served from cache |
| `cacheWriteInputTokens` | prompt tokens written into cache |
| `reasoningOutputTokens` | reasoning subset reported by the provider; preserved, not added twice |
| `processedTokens` | fresh input + cached input + cache write + output |

`processedTokens` is a **raw throughput counter**, defined solely as the sum
above. `processedTokens != billing / plan usage`. Cache and fresh tokens may
have different economic meaning, and provider raw counts must not be presented
as a cost comparison. No pricing is applied.

A field a provider does not report is omitted from the record rather than
guessed or zero-filled.

## Record shape

```json
{
  "run": "admin-presentation",
  "schemaVersion": 1,
  "agents": [
    {
      "invocationId": "planner-r1",
      "provider": "claude",
      "role": "planner",
      "round": 1,
      "model": "claude-opus-5",
      "startedAt": "2026-08-21T15:09:30.032Z",
      "finishedAt": "2026-08-21T15:14:02.881Z",
      "durationMs": 272849,
      "inputTokens": 0,
      "outputTokens": 0,
      "cachedInputTokens": 0,
      "cacheWriteInputTokens": 0,
      "reasoningOutputTokens": 0,
      "processedTokens": 0,
      "sourceId": "a71b007356e7bb441",
      "source": "<provider transcript identifier or path>",
      "transcriptPath": "<path supplied to the provider adapter>",
      "collectedAt": "2026-08-21T15:14:03.000Z"
    }
  ]
}
```

`agents` is the raw data. Per-role subtotals, per-round breakdown, share
percentages and the grand total are **derived by the local reporter**, not
stored, so a stored summary can never drift from the records.

## Measurement scope

Every record carries `measurementMode`, because not all roles are measured the
same way:

| mode | meaning |
|---|---|
| `invocation` | one agent spawn, scanned from that invocation's own transcript |
| `run_delta` | difference between two cumulative snapshots taken at the run boundary |
| `session_cumulative` | legacy only: a whole-session figure, scope unknown relative to the run |

`planner` / `implementer` / `reviewer` are `invocation`. The `orchestrator`
drives the run from a session that outlives it, so it is `run_delta`: the run
document stores a `runBoundary` with the baseline snapshot taken at run start,
and the orchestrator record is the end snapshot minus that baseline.

```json
"runBoundary": {
  "provider": "claude",
  "sessionId": "...",
  "startedAt": "...",
  "endedAt": "...",
  "measurementMode": "run_delta",
  "baseline": { "inputTokens": 0, "outputTokens": 0, "cacheReadTokens": 0, "cacheCreationTokens": 0 },
  "sessionCumulative": { "...": 0 }
}
```

A delta of two snapshots is preferred over filtering events by timestamp: a run
boundary cannot then fall inside a single response that spans several transcript
lines, and tokens spent before the run started are never attributed to it.

Only records sharing a comparable scope go in the comparison table.
`session_cumulative` records are reported separately and are never recomputed
into a delta — a cumulative total carries no information about where its run
began. `sessionCumulative` is reference information for `--detail` only.

A per-field negative delta means the transcript changed under the baseline. It
is a monitoring warning, never a recorded value.

## Run-level aggregation

- Group records by `role`; sum each token field across all rounds of that role.
- Grand total = sum over every record.
- Reports group by provider, then split Agent subtotal (planner, implementer,
  reviewer), Orchestrator, and Overall.
- Rounds are additionally listed individually so fix-round cost stays visible.

## Storage

`_workspace/{slug}/usage.json`, alongside the run's `plan.md` / `impl_rN.md` /
`review_rN.md`. `_workspace/` stays gitignored: usage logs are never committed.
The JSON is the only stored artifact; the human-readable table is produced on
demand by the CLI.

## Collection constraints

- Collection is performed by a **local script**, never by an AI agent. Spawning
  an agent to read or analyze a transcript is prohibited — the measurement would
  consume the thing it measures.
- Transcripts are read line by line; the full transcript is never loaded into
  memory and never enters any agent's context.
- Only numbers and the minimal metadata above are recorded. No transcript
  content is copied into the record.
- Collector failure is a **monitoring warning**, never a build/verification
  failure. It cannot make a feature FAIL.

## Not in scope (yet)

Token budgets, thresholds and forced stops are deliberately not implemented.
Data is collected first so a budget can later be chosen from real numbers. The
adapter interface and record shape leave room for that without redesign.

## Provider adapter interface

An adapter resolves a role + round + optional provider agent id into one record
of the shape above:

```
collect({ runSlug, role, round, sourceId?, sessionId? }) -> record | { warning }
```

Adapters live under `scripts/harness-usage/providers/`. Adding a provider means
adding one adapter file; the schema, reporter and storage stay unchanged. A
provider whose real usage source has not been inspected in this environment is
not implemented on speculation.

## Shared history record

The per-run document above is the collector's working format. The long-term
history (`.harness/metrics/raw/usage-history.jsonl`) stores one **normalized**
record per invocation, produced by `scripts/harness-usage/lib/schema.mjs`. Claude
and Codex must both be expressible in exactly these fields; a provider-specific
field name never appears here.

| field | type | meaning |
|---|---|---|
| `timestamp` | ISO string | when the invocation finished (or was collected) |
| `provider` | `claude` \| `codex` | runtime that produced the usage |
| `harnessVersion` | semver \| null | `.harness/VERSION` at record time |
| `runId` | string \| null | Harness run slug; null when unattributed |
| `role` | `planner` \| `implementer` \| `reviewer` \| `orchestrator` \| `unknown` | logical Harness role, never a provider agent name |
| `lane` | `A` \| `B` \| `C` \| null | Workflow Lane |
| `laneSource` | `declared` \| `artifact` \| `inferred` \| null | how the Lane was established |
| `round` | integer ≥ 1 | 1 for the first pass, 2+ for fix rounds |
| `model` | string \| null | model id the provider reported |
| `status` | `completed` \| `unknown` | whether the invocation was observed finished |
| `durationMs` | number \| null | last event minus first event |
| `inputTokens` | number | fresh prompt tokens |
| `outputTokens` | number | generated tokens |
| `cacheReadTokens` | number | prompt tokens served from cache |
| `cacheWriteTokens` | number | prompt tokens written to cache |
| `reasoningTokens` | number | reasoning subset the provider reports (0 when it reports none) |
| `processedTokens` | number | `input + output + cacheRead + cacheWrite` |
| `measurementMode` | `invocation` \| `run_delta` | see above |
| `attribution` | `harness` \| `auto` | whether the Harness stated the role/run or the monitor detected it |
| `sourceId` | string \| null | **raw local only**; stripped from every committed file |
| `quality` | object \| null | `reviewerFirstPass`, `revisionRounds`, `typecheckPassed`, `lintPassed`, `buildPassed`, `testPassed` — each independently nullable |

`processedTokens != billing cost`, `processedTokens != subscription usage`,
`processedTokens != actual charged tokens`. It is a throughput counter and
nothing else; reasoning output is a subset the provider reports separately and
is deliberately not added into it a second time.

A value the provider does not report is `null` (unknown), never a guess. Token
dimensions a provider genuinely does not have are `0`.

Identity for deduplication is `provider + sourceId` (falling back to
`runId:role:round`). The history is append-only; readers keep the highest
`attribution` per identity, so the same invocation observed twice — once
auto-detected, once collected by the Harness — is stored once.
